# Spike I6 — `ASTParser.createASTs` batch en Java

**Fecha:** 2026-10-18 18:05
**Autor:** Claude Code
**Árbol:** `<WORKSPACE>\Sourcetrail-profundo\neo-sourcetrail`
**Objetivo:** medir si `createASTs` (un environment para N archivos) es más rápido que
el camino de producción (`ASTParser` nuevo + `setEnvironment` + `createAST` por archivo)
sin degradar los bindings, antes de tocar el contrato JNI.

---

## 1. Método

Spike `docs/Claude-Code/spikes/JdtBatchSpike.java` (JDT 3.44, compliance 21), sobre los 128 archivos de
`bin/app/user/projects/javaparser/src/main/java`:

- **Per-file (producción):** por cada archivo, `ASTParser.newParser(...)`,
  `setEnvironment(classpath vacío, source root, bootclasspath=true)`, `setSource`,
  `createAST`. Se recorre el AST llamando `SimpleName.resolveBinding()` y se cuentan
  bindings no nulos y problemas (`CompilationUnit.getProblems()`).
- **Batch:** un `ASTParser` por lote de 50, `setEnvironment` una sola vez,
  `createASTs(paths, "UTF-8", ...)`; el `FileASTRequestor` recorre cada
  `CompilationUnit` con el mismo conteo.
- Calentamiento de JIT con 3 archivos antes de medir. Ambos modos ven el mismo contenido
  (sin el reemplazo de tabs de producción; ver §4).

## 2. Resultados

```
files: 128, sourceRoot: .../javaparser/src/main/java, batch: 50
per-file:   11.385 ms total, 88,9 ms/file, bindings=35.106, problems=105
batch:         882 ms total,  6,9 ms/file, bindings=35.106, problems=105
speedup:  12,91x
binding delta (batch - per-file): 0
```

| Métrica | Per-file | Batch |
|---|---|---|
| Tiempo | 11,385 s | **0,882 s** |
| Por archivo | 88,9 ms | **6,9 ms** |
| Bindings resueltos | 35.106 | **35.106** |
| Problemas | 105 | **105** |

El batch es **12,9×** más rápido en parseo+bindings y produce exactamente los mismos
bindings y problemas. La degradación que había sufrido la reutilización de `ASTParser`
(§4 de `09_...`) **no aparece** con `createASTs`.

## 3. Impacto end-to-end

Indexado real del proyecto javaparser con el build actual (4 hilos):

```
sourcetrail_cli.exe javaparser.srctrlprj  ->  18,4 s
nodes 4.126, edges 25.601, files 138
```

Estimación con 4 hilos (`getIdealThreadCount(false)` = 4):

- CPU total: 18,4 s × 4 ≈ **73,6 CPU‑s**.
- Parseo+bindings: 128 × 88,9 ms ≈ **11,4 CPU‑s** (15,5 %).
- Batch: 128 × 6,9 ms ≈ **0,9 CPU‑s**.
- Ahorro: **~10,5 CPU‑s ≈ 2,6 s de pared (~14 %)** en javaparser.

En kafka (6.177 archivos) el ahorro absoluto es mayor (~8,5 CPU‑min) pero sigue acotado
por la fracción de parseo; el resto es el visitor + escritura en SQLite, que no cambia.

## 4. Bloqueantes de integración

1. **Contrato JNI de un archivo por llamada.** `JavaIndexer.processFile(address, path,
   content, ...)` y `TaskBuildIndex` llaman una vez por archivo. Haría falta un
   `processFiles(...)` batch, bufferizar por thread en `JavaParser` y vaciar al final.
2. **Estado por archivo en C++.** Los callbacks (`recordSymbol`, `recordReference`, …)
   usan `m_currentFileId`/`m_currentFilePath`, que hoy se fijan antes de la llamada JNI.
   En un batch, la parte Java debe avisar el inicio de cada archivo (nuevo native
   `beginFile(parserId, path)`) o el C++ debe mapear path→fileId y pasarlo.
3. **`createASTs` lee los archivos del disco.** El camino actual pasa el contenido ya
   decodificado (y sin tabs) por JNI. Para batch habría que: (a) dejar que JDT lea el
   archivo y asumir UTF‑8, con riesgo para fuentes no UTF‑8; o (b) escribir copias
   temporales con el contenido transformado y mapear las rutas de vuelta.
4. **Tabs.** Producción reemplaza `\t` por un espacio (1:1, no expande). El spike usó el
   contenido original y los bindings fueron idénticos; si se usa `createASTs` sobre el
   archivo original, hay que verificar que las columnas del visitor sigan coincidiendo
   (JDT cuenta caracteres, pero no se probó el visitor de Sourcetrail con tabs).

## 5. Decisión

**Spike cerrado; no se implementa el batch JNI por ahora.** El 12,9× es real pero se
aplica sólo al 15 % del costo del indexado Java; el end-to-end es ~14 % en javaparser.
El cambio requiere contrato JNI nuevo, bufferizado por thread, manejo de contenido y
encoding, y estados por archivo: riesgo medio-alto para un ahorro acotado.

Si el indexado Java pasa a ser el cuello de botella, el diseño de menor riesgo es:
bufferizar en `JavaParser` (N=32), `processFiles` con paths, `beginFile` por archivo, y
copias temporales sólo si la verificación de tabs/encoding lo exige.
