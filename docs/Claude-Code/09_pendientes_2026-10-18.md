## 3. I1/I2 — Batch/daemon del indexer Python

**Costo actual medido** (10 iteraciones, máquina ociosa):

| Comando | Tiempo |
|---|---|
| `python -X utf8 -c pass` | 98 ms |
| `import jedi` | 398 ms |
| `import parso` | 242 ms |
| `import numbat` | 136 ms |
| `import jedi, parso, numbat` | 448 ms |
| `run.py --version` (imports incluidos) | **437 ms** |

El arranque de `run.py` es ~0,44 s, pero el costo fijo real por archivo es mayor: cada
proceso abre la base, verifica la versión y arranca jedi en frío.

**Spike de batch** (21 archivos de tutorial-py,
`docs/Claude-Code/spikes/py_batch_spike.py`):

| Modo | Tiempo | Por archivo | Counts (nodos, edges, archivos) |
|---|---|---|---|
| Un proceso (base abierta, jedi caliente) | **13,43 s** | 640 ms | (104, 395, 21) |
| Un proceso por archivo | **32,83 s** | 1.563 ms | (104, 395, 21) |

**2,44×** en serie y counts idénticos. El overhead fijo es ~0,92 s/archivo; en
matplotlib (913 archivos, 4 workers) son ~210 s = **3,5 min de 56,6 min (~6 %)**.
En tutorial (corpus chico) el ahorro relativo es ~29 %.

**Qué haría falta (diseño de menor riesgo):** un daemon transparente **por base** (cada
thread de C++ usa una base distinta), escuchando en un named pipe, con timeout de
inactividad. El cliente `run.py` sería un lanzador liviano (sin importar jedi) que
reenvía la solicitud; el daemon mantiene la base abierta y los imports calientes. No
requiere cambios en C++ ni en el contrato del comando, y preserva el paralelismo (un
daemon por base/thread). Riesgos: procesos huérfanos (mitigado con timeout), dos
conexiones SQLite a la misma base (WAL ya lo soporta) y propagación de errores.

**Decisión:** no implementarlo en esta ronda. El ahorro es ~6 % en corpus grandes y el
cambio de ciclo de vida del proceso merece su propia validación. Queda documentado con
el diseño y el spike reproducible.

## 4. I6 — `ASTParser.createASTs` batch en Java

`JavaIndexer.processFile` crea un `ASTParser`, configura el environment con classpath y
source roots, y llama `createAST` por archivo. `createASTs` permite parsear varios
archivos con un solo environment.

**Bloqueante:** el contrato JNI es de un archivo por llamada
(`processFile(address, filePath, fileContent, ...)`), y el scheduler llama una vez por
archivo. Habría que agregar una llamada batch que reciba N pares (path, content) y
recorra los `CompilationUnit` con el mismo visitor. Ya se probó reutilizar un
`ASTParser` entre archivos y **degradó los bindings** (javaparser 4126/25.601 →
2883/8.320), así que el único camino seguro es `createASTs`.

**Spike realizado (ver `10_spike_i6_2026-10-18.md`):** `createASTs` es **12,9×** más
rápido en parseo+bindings (6,9 vs 88,9 ms/archivo) con bindings y problemas idénticos.
Pero el parseo es ~15 % del costo total del indexado Java, así que el ahorro end-to-end
es ~14 % (2,6 s de 18,4 s en javaparser). **Decisión:** no implementar el batch JNI por
ahora; requiere contrato nuevo, bufferizado por thread y manejo de contenido/encoding.
