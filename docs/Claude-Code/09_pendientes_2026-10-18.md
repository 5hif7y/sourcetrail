## 3. I1/I2 — Batch/daemon del indexer Python

**Costo actual medido** (10 iteraciones, máquina ociosa):

| Comando | Tiempo |
|---|---|
| `python -X utf8 -c pass` | 98 ms |
| `import jedi` | 398 ms |
| `import parso` | 242 ms |
| `import numbat` | 136 ms |
| `import jedi, parso, numbat` | 448 ms |
| `run.py --version` (imports incluidos) | **437 ms** |

El arranque real es ~0,44 s por archivo, no 0,94 s. Con 913 archivos y 4 workers son
~100 s de 56,6 min: **~3 %**, no 6 %. El resto del tiempo por archivo es trabajo real de
indexado (jedi + escritura en la base).

**Qué haría falta:** un proceso persistente por worker con un protocolo por stdin, y
cambios en `TaskExecuteCustomCommands`/`IndexerCommandCustom` para agrupar archivos.
Riesgos: el proceso y el `PersistentStorage` de C++ mantendrían dos conexiones SQLite
abiertas a la misma base por thread; el estado de jedi (caches por entorno) crecería
entre archivos; la interrupción y el manejo de errores cambian.

**Decisión:** no implementarlo mientras el ROI siga en ~3 % y el modelo por archivo sea
más robusto. Queda documentado para retomarlo si el indexado Python pasa a ser el cuello
de botella principal.

## 4. I6 — `ASTParser.createASTs` batch en Java

`JavaIndexer.processFile` crea un `ASTParser`, configura el environment con classpath y
source roots, y llama `createAST` por archivo. `createASTs` permite parsear varios
archivos con un solo environment.

**Bloqueante:** el contrato JNI es de un archivo por llamada
(`processFile(address, filePath, fileContent, ...)`), y el scheduler llama una vez por
archivo. Habría que agregar una llamada batch que reciba N pares (path, content) y
recorra los `CompilationUnit` con el mismo visitor. Ya se probó reutilizar un
`ASTParser` entre archivos y **degradó los bindings** (javaparser 4126/25.601 →
2883/8.320), así que el único camino seguro es `createASTs`.

**Decisión:** no implementado. Es un cambio de contrato JNI de riesgo medio para un
ahorro de ~0,19 s/archivo. Se deja como spike futuro.
