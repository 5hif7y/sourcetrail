# Odin nativo: indexador en Odin + writer C

**Fecha:** 2026-10-19
**Árbol:** `<WORKSPACE>\Sourcetrail-profundo\neo-sourcetrail`
**Objetivo:** reemplazar el PoC Python por un indexador **escrito en Odin**, sin
dependencia de Python en runtime, y dejarlo listo para el refactor de plugins.

---

## 1. Resultado

El indexador nativo funciona de punta a punta:

- `src/odin_indexer/main.odin`: lexer, scanner de declaraciones, resolución
  paquete/imports y escritura de nodos/aristas.
- `src/odin_writer/`: shim C sobre `SourcetrailDBWriter` (SourcetrailDB core, SQLite
  embebido). Lo usa Odin por FFI (`foreign import`).
- `src/odin_indexer/build.ps1`: compila el shim, compila el indexador con Odin y copia
  `SourcetrailOdinIndexer.exe` + `sourcetrail_odin_writer.dll` a
  `bin/app/data/odin` y a los dos builds.
- `SourceGroupSettingsOdinEmpty` prefiere el ejecutable nativo y deja el script Python
  como fallback.

**No hay Python en el camino nativo.** El único runtime extra es la DLL del writer,
que lleva SQLite embebido.

## 2. Arquitectura

```text
sourcetrail_cli
  └─ TaskExecuteCustomCommands
       └─ SourcetrailOdinIndexer.exe index --source-file-path=... --database-file-path=...
            ├─ lexer + parser Odin (main.odin)
            ├─ tabla de símbolos del paquete + imports locales
            └─ sourcetrail_odin_writer.dll
                 └─ SourcetrailDBWriter (sourcetrail-db core + SQLite)
```

- Nombres completos: `paquete.simbolo`, `paquete.Struct.campo`,
  `paquete.Enum.variante`. El writer los separa por `.` y crea la jerarquía.
- Referencias: `TYPE_USAGE`, `USAGE`, `CALL`, `IMPORT`, `INHERITANCE` (`using`).
- El source group sigue siendo `ODIN_EMPTY`; `Project.cpp` lo manda por
  `TaskExecuteCustomCommands` (igual que Python).
- La DLL se carga desde el directorio del `.exe` nativo; el build script las copia
  juntas.

## 3. Resultados

### 3.1 Sample del repo

| Indexador | Archivos | Nodos | Aristas | Errores | Tiempo de indexado |
|---|---:|---:|---:|---:|---:|
| Python PoC | 3 | 32 | 53 | 0 | 1,1 s |
| **Odin nativo** | 3 | 32 | **42** | 0 | 1,4 s (desktop), 1,1 s (embedded) |

La diferencia de aristas es de **member edges duplicados** del writer Python/numbat:
los tipos de arista semánticos (`USAGE`, `TYPE_USAGE`, `CALL`, `INHERITANCE`,
`IMPORT`) coinciden exactamente. El writer C++ deduplica los member edges.

### 3.2 Código real de Odin

| Proyecto | Indexador | Archivos | Nodos | Aristas | Errores | Tiempo |
|---|---|---:|---:|---:|---:|---:|
| `core/strings` | Python | 6 | 349 | 1.902 | 0 | 5,28 s |
| `core/strings` | **Odin** | 6 | 348 | 1.471 | 0 | 2,1 s |
| `core/bufio` + `core/fmt` | Python | 11 | 612 | 2.919 | 0 | 5,12 s |
| `core/bufio` + `core/fmt` | **Odin** | 11 | 612 | 1.978 | 0 | 3,2 s |

Otra vez, la diferencia son member edges duplicados; los nodos y las referencias
semánticas coinciden. El indexador nativo es más rápido y no necesita Python.

### 3.3 Builds

- Desktop: `sourcetrail_cli` y `Sourcetrail` compilan; el sample se abre en la GUI.
- Embedded: `sourcetrail_cli` compila y usa el indexador nativo.
- Tamaños: `SourcetrailOdinIndexer.exe` 729.600 B; `sourcetrail_odin_writer.dll`
  868.352 B; deploy adicional ≈ 1,6 MB.

## 4. Build y despliegue

```powershell
# Compilador de Odin usado en este host:
#   C:\Software\Odin-oct-2026\odin.exe
.\src\odin_indexer\build.ps1 `
  -Odin "C:\Software\Odin-oct-2026\odin.exe"

# El script:
#  1. compila src/odin_writer con CMake/VS 18 y SourcetrailDB (hermano);
#  2. copia el .lib al directorio del indexador;
#  3. compila main.odin con Odin;
#  4. copia exe + DLL a bin/app/data/odin, build/Release/app/data/odin y
#     build-embedded/Release/app/data/odin.
```

El `copyAppData` del CMake raíz copia `bin/app/data/odin` cuando existe, así que un
build completo también despliega el indexador.

Requisitos:

- Visual Studio 18 2026 (o el generador que corresponda).
- `sourcetrail-db` como hermano de `neo-sourcetrail`, o
  `-DSOURCETRAILDB_DIR=<ruta>` al compilar el writer.
- Compilador de Odin (`odin` en PATH o `-Odin <ruta>`).

## 5. Limitaciones

1. El parser sigue siendo **aproximado**: no hace type checking, no resuelve
   genéricos/sobrecargas y sólo resuelve el paquete actual + imports locales directos.
2. El shim depende del repo hermano `sourcetrail-db` para compilar; no está vendorizado
   en el fork.
3. El build script es Windows/VS; falta una variante Linux.
4. No hay tests automatizados del indexador nativo; los números son de ejecuciones
   manuales.
5. Los binarios no se commitean (están en `.gitignore`); el build script los produce.
6. El writer C++ crea un `.srctrlprj` si la DB no existe; en el core la DB temporal ya
   existe, así que no se usa ese camino.
7. El fallback Python sigue disponible con `SOURCETRAIL_ODIN_NATIVE_INDEXER` apuntando
   a una ruta inexistente o si no se desplegó el ejecutable nativo.
