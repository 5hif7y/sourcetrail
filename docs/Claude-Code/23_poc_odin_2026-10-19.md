# PoC de Odin: resultados de prueba y experimentación

**Fecha:** 2026-10-19
**Árbol:** `<WORKSPACE>\Sourcetrail-profundo\neo-sourcetrail`
**Objetivo:** validar el soporte de Odin de punta a punta con el modelo actual
(indexador externo por archivo + `SourceGroupSettingsCustomCommand`) **antes** de
refactorizar el sistema de plugins del doc 21.

---

## 1. Qué se implementó

| Pieza | Archivo |
|---|---|
| Source group `ODIN_EMPTY` | `src/lib/settings/source_group/SourceGroupType.*` |
| Lenguaje `LanguageType::ODIN` | `src/lib/settings/LanguageType.*` |
| Settings del source group | `src/lib/settings/source_group/type/SourceGroupSettingsOdinEmpty.*` |
| Fábrica | `src/lib/project/SourceGroupFactoryModuleOdin.*` |
| Ruteo a comandos custom | `src/lib/project/Project.cpp` |
| Registro en CLI/API/GUI | `src/cli/main.cpp`, `src/lib_api/libsourcetrail.cpp`, `src/app/main.cpp`, wizard Qt |
| Indexador Odin | `bin/app/data/python/SourcetrailOdinIndexer/run.py` |
| Proyecto de ejemplo | `bin/app/user/projects/odin-sample/` |

El indexador es **Python + numbat** (el mismo binding que usa el indexador Python) y
hace todo el trabajo por archivo:

```text
python -X utf8 run.py index \
  --source-file-path=<archivo> \
  --database-file-path=<db>
```

`SourceGroupCustomCommand` ya se encarga de ejecutar el comando por archivo, crear las
DB temporales por hilo y fusionarlas. `Project.cpp` ahora incluye `ODIN_EMPTY` en la
rama que manda los comandos a `TaskExecuteCustomCommands` (sin ese cambio, el core
intentaba enviar un `IndexerCommandCustom` por IPC y fallaba con “type unknown”).

## 2. Por qué no se usó tree-sitter en este PoC

El estudio 22 mostró que la gramática `tree-sitter-odin` de mayo de 2023 falla en
**1.187 de 1.416** archivos de `core` + `base` (83,8 %), y en **todos** los 305 que
empiezan con `#+build`. Para validar la integración con Sourcetrail —que era el
objetivo del PoC— se escribió un **scanner propio**: lexer + reconocimiento de
declaraciones y referencias, sin parser generado. No pretende ser un parser completo
de Odin; sí cubre lo necesario para la navegación.

Esto deja la decisión del parser final abierta: actualizar/forkear tree-sitter
(recomendación del doc 22) o promover este scanner a C++. El PoC no cierra esa
decisión.

## 3. Qué indexa

- `package`, `import` (con alias), `foreign import` (ignorado como import externo).
- `struct`, `union`, `enum` y variantes, `bit_set`, `bit_field`, `distinct`.
- `proc` con parámetros, resultado, `where`, cuerpo y directivas (`#force_inline`,
  `#optional_allocator_error`, etc. se saltan).
- Campos, constantes/variables de paquete, parámetros polimórficos `$T` (se ignoran
  como referencia).
- Llamadas (`CALL`), usos (`USAGE`), usos de tipo (`TYPE_USAGE`), imports (`IMPORT`) y
  `using` como `INHERITANCE`.
- `#+build`, `#assert`, `@(...)`, `when ... { ... } else { ... }` y comentarios se
  procesan sin romper el archivo.

**Resolución:** tabla de símbolos del **paquete actual** (archivos `.odin` del mismo
directorio) más los **imports locales directos** resueltos contra el directorio del
archivo. Los imports `core:`, `base:` y `vendor:` se tratan como externos. No hay
resolución semántica de genéricos, sobrecargas ni tipos; las referencias no resueltas
se omiten (no se inundan de “unsolved”).

## 5. Limitaciones conocidas

1. **Dependencia de Python + numbat** en el target; el PoC no es un plugin nativo.
2. **Resolución limitada:** sólo paquete actual + imports locales directos; no hay
   tipos, genéricos, sobrecargas ni `foreign` real.
3. **Tabla de símbolos por paquete:** se reescanea por cada archivo. Con paquetes
   chicos es barato; con proyectos grandes conviene caché o el indexador nativo.
4. **No hay pruebas automatizadas** todavía; los resultados son de ejecuciones
   manuales.
5. **El wizard** compila y el caso está agregado, pero no se recorrió el diálogo
   completo de creación; se validó abriendo un proyecto existente.
6. **No reemplaza al C++/Java:** el .odin se indexa como texto; las macros y la
   semántica de Odin no se evalúan.

## 6. Qué sigue

1. **Refactor de plugins (doc 21, F0–F3):** mover este lenguaje a un descriptor/plugin
   con `Effect`/`inject` y carga/descarga segura.
2. **Decidir parser final:** actualizar tree-sitter con `odin.ebnf` o promover el
   scanner a un lexer/parser C++ con tests de cobertura. La recomendación del doc 22
   sigue siendo actualizar la gramática; el PoC demuestra que un scanner acotado
   también puede entregar navegación útil.
3. **Resolver cross-file** con una tabla de proyecto compartida (indexador nativo) o
   caché por paquete.
4. **Tests:** sample + `core/strings` + `core/bufio`/`fmt` como gates de CI; comparar
   counts y navegación.
5. **GUI:** recorrer el wizard y verificar creación/edición de un source group Odin.

## 7. Reproducir

```powershell
# desktop
cmake --build build --config Release --target sourcetrail_cli
Copy-Item bin/app/data/python/SourcetrailOdinIndexer/run.py `
  build/Release/app/data/python/SourcetrailOdinIndexer/run.py -Force
build/Release/app/sourcetrail_cli.exe `
  bin/app/user/projects/odin-sample/odin-sample.srctrlprj --refresh=all

# embedded
cmake --build build-embedded --config Release --target sourcetrail_cli
Copy-Item bin/app/data/python/SourcetrailOdinIndexer/run.py `
  build-embedded/Release/app/data/python/SourcetrailOdinIndexer/run.py -Force
build-embedded/Release/app/sourcetrail_cli.exe `
  bin/app/user/projects/odin-sample/odin-sample.srctrlprj --refresh=all
```

El PoC queda como referencia experimental. No es la arquitectura final: el refactor de
plugins del doc 21 es el que convierte a Odin en un lenguaje independiente y
descargable.
